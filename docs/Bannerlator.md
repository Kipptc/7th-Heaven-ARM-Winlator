# Bannerlator build and test notes

## Current game crash investigation

V37 bounds and synchronizes virtual IRO file seeks and reads. The previous implementation could seek past EOF, cast a negative remaining length to `uint`, then copy beyond its byte array on the next read. The local seek/read harness passed, and the AnyCPU `AppWrapper.dll` was uploaded and SHA256 verified. An initial x86-only upload prevented the ARM64 UI from starting; it was immediately replaced with AnyCPU, after which the user confirmed the UI opened. The next game run reached the first battle and XP/gil screen, then crashed on return to the field. Its Wine log shows the same .NET 10 CoreCLR access violation at `coreclr+0xe22ab` and fatal `0x80131506` as the earlier FMV-to-field crash. V37 therefore did not resolve the remaining runtime failure.

V38 sets `DOTNET_EnableWriteXorExecute=0` inside Wine `ff7_en.exe` before `hostfxr_initialize_for_runtime_config`, unless the container has set it explicitly. This follows a [FEX CoreCLR issue](https://github.com/FEX-Emu/FEX/issues/5766) reporting the same fatal error and a partial workaround with this setting. `AppLoader.log` now writes to `D:\Bannerlator\FINAL FANTASY VII (2013)` when that directory exists, so the setting can be checked over FTP. The Win32 loader build passed and the uploaded DLL matched on FTP read-back. The user's first device run with v38 completed the initial sequence, 11 battles, the in-game 7th Heaven Bar cutscenes, and a save in Beginner's Hall. The loader log confirms the setting applied before x86 .NET startup. FFNx logged all 11 battle completions and the save without errors; its only warning was a missing `data/music_ogg/config.toml`, for which it used defaults. The wrapper loaded the four selected mods and logged no exceptions. This is one successful extended run, not yet proof of long-term stability. The full `7thHeaven-Bannerlator-arm64-v38.zip` contains the same 887 files as v36, with only `AppLoader.dll`, `AppWrapper.dll`, and `BANNERLATOR-README.txt` changed; key archive entries were verified by SHA256 and no custom FFNx binary is included.

## Stock FFNx and device log export

V36 uses the [prebuilt stock FFNx release](https://github.com/julianxhokaxhiu/FFNx/releases) through 7th Heaven's existing automatic download. On a fresh Steam 2013 installation, Play queues that download; press Play again when it finishes. On Wine startup, 7th Heaven copies the previous game's `FFNx.log` to `D:\Bannerlator\FINAL FANTASY VII (2013)\FFNx.log` if the source is newer. Play makes the same check. This keeps FFNx itself unchanged while making crash logs accessible over device FTP after reopening 7th Heaven. The ARM64 publish passed; the two changed DLLs, `7th Heaven.dll` and `AppCore.dll`, were backed up on the device, uploaded, and SHA256 verified by FTP read-back.

V35 adds custom FFNx deployment to the Bannerlator Play path. Put modified FFNx files under a `FFNx` directory beside `7th Heaven.exe`, preserving paths relative to FF7's game folder (for Steam 2013 the driver is `FFNx\AF3DN.P`). Play copies changed files, stores each pre-custom original once under the game's `.7h-ffnx-original`, and records deployed hashes in `.7h-custom-ffnx.json`. It reapplies non-TOML files if another process replaces them. FFNx.toml is validated before copying and is not reapplied unchanged, so normal 7H/FFNx setting changes remain effective. If a new tester lacks FFNx, Play queues the stock FFNx download first, then applies staged custom files after extraction or on the next Play. Once a custom driver exists, routine and manual updater operations preserve it; removing the custom deployment marker and staging folder returns to stock update behavior. A local fixture passed original backup, no-op repeat Play, and replacement recovery. The ARM64 publish passed; AppCore.dll and 7th Heaven.dll were uploaded and FTP SHA256 read-back matched.

## Build a portable package

Build the Release solution on Windows with the .NET 10 SDK, the Visual Studio C++ toolchain, and the repository's vcpkg dependencies. The solution build must produce the Win32 `AppLoader.dll` and `nethost.dll` in `AppUI/bin/Release/net10.0-windows7.0`.

Then run `tools/Publish-Bannerlator.ps1`. It publishes the x64 WPF UI with its .NET Desktop Runtime, adds the Win32 loader, and installs a private x86 .NET Runtime in `runtime-x86`. Copy the resulting `.dist/Bannerlator` directory into the Wine container and launch `7th Heaven.exe` from it. Keep the directory intact; `AppLoader` reads `7thHeavenRuntime.ini` beside `ff7_en.exe` to locate the private runtime when Bannerlator starts FF7. It also accepts `SEVENTH_HEAVEN_DOTNET_ROOT_X86` for direct launches. The script downloads the x86 runtime using Microsoft's `dotnet-install.ps1`.

For a native ARM64 UI, run `tools/Publish-Bannerlator.ps1 -UiRuntimeIdentifier win-arm64 -OutputDirectory .dist/Bannerlator-arm64`. This requires the ARM64 `d3dcompiler_47.dll` from the Windows 10 SDK redistributables; the script copies it beside the EXE and checks its machine type. The 32-bit game loader still uses the separate x86 runtime.

The Bannerlator build sets `System.Globalization.UseNls` in both runtime configuration files. This keeps culture support while avoiding .NET's ICU path. Under Wine, 7th Heaven also asks WPF to render its own UI in software. FF7 and its graphics driver retain their normal GPU path.

The shared combo box template no longer uses an unused `VisualStateGroup`. On Proton 11 ARM64EC, loading General Settings previously threw a `NullReferenceException` from `VisualStateGroup.get_States` while applying that template.

The v2 and v3 application logs show a separate WPF failure: `SystemColors.HighlightBrushKey` throws while WPF loads a built-in `ListBoxItem` theme for General Settings. A later `XamlParseException` occurs while the app tries to show its error UI. A v4 attempt to suppress list item theme lookup made sections of the form white, so it was reverted. The v5 x64 UI uses the original list controls and reads the FF7 and library path text directly under Wine. The file picker returned the correct path in the v4 log, but its binding did not keep the path visible.

The native Windows ARM64 UI test is self-contained and avoids the x64 emulation path that triggered these WPF errors. Its first test failed before the UI opened because `wpfgfx_cor3.dll` needed an ARM64 `d3dcompiler_47.dll`, while Bannerlator's System32 copy was x64. The corrected v2 ARM64 test includes the Windows SDK ARM64 redistributable copy next to the application. The user confirmed that v2 opens and that General Settings works.
